Linux Kernel Architecture — Architectural Approaches and Styles

Not a Layer Cake

Most diagrams draw the Linux kernel as a stack: applications on top, system calls below them, then subsystems, then drivers, then hardware. That picture is wrong twice. It implies walls between subsystems, when in fact the kernel is a monolith — one address space and one failure domain, where the only real boundary is the one with userspace. And it implies that work descends through every layer in order, when real paths skip layers: mmap bypasses the read() path, XDP intercepts packets before the network stack, and io_uring sidesteps part of the VFS call path.

The Narrow Waist

The architecture of the Linux kernel is better described as one pattern repeated at many scales: the narrow waist. Many callers above, one contract structure in the middle, many implementations below. The contract is almost always a struct holding a table of function pointers — object orientation implemented by hand in C, with struct embedding for inheritance and container_of() for the downcast.

  • struct file / file_operations — the VFS waist between every file syscall and every filesystem, from ext4 and btrfs to procfs and FUSE.
  • sk_buff / net_device_ops — the network waist: protocols above never name a driver, drivers below never name a protocol.
  • struct bio / request_queue — the block waist, which is why device mapper and md RAID can stack on top of NVMe.
  • sched_class — scheduler classes (stop, deadline, rt, fair, idle, ext) as interchangeable policy behind one core mechanism.
  • tcp_congestion_ops — pluggable congestion control (cubic, BBR, Reno, DCTCP and more), a waist nested inside the network waist.
  • security_hook_heads — Linux Security Module hooks, where the subsystem places the hook and SELinux, AppArmor, Landlock or a BPF program makes the decision.

Mechanism Versus Policy

Each waist separates mechanism from policy: the kernel keeps the mechanism and lets the policy be swapped. That is why changing the TCP congestion control algorithm or the I/O scheduler is a sysctl rather than a rebuild, and why cgroup controllers, LSM modules and scheduler classes plug in rather than fork the tree.

Concurrency, Context and Deferred Work

Two further architectural decisions shape the code everywhere. First, context is a permission: a hard interrupt handler cannot sleep, so it does the minimum and defers the rest to a softirq, a workqueue or a kernel thread — the top-half/bottom-half split, of which NAPI is the network example. Second, scalability comes from removing shared writable state rather than from finer locks: RCU lets readers run without locks while a writer publishes a copy, with reclamation deferred until a grace period ends, alongside seqlocks and per-CPU data.

Stable ABI, Unstable Internals, and eBPF

The userspace ABI is never broken, while the in-kernel API is deliberately unstable: there is no stable module interface, which is what makes tree-wide refactoring possible. Hardware is described as data through Device Tree and ACPI rather than as code, and the newest architectural layer is eBPF — verified, JIT-compiled programs attached at kprobes, tracepoints, XDP, tc, LSM hooks and sched_ext, which lets userspace supply kernel policy without a module.
